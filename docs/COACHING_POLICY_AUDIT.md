# Coaching policy audit

Generated by writing the rationale fixtures, not by reading the code.
`tests/test_recommend_snapshots.py` holds the evidence and re-checks every
claim on this page on each run.

Four defects. Three of them mean the policy is quieter than it looks.

## 1. `deload` cannot be produced

This is the important one.

```
loadcalc.acwr(acute, chronic) -> round(acute / chronic, 2)
recommend: HIGH_ACWR = 1.5
```

`acute` is the 7-day combined load and `chronic` is the 28-day combined load.
Both are sums of non-negative per-session loads over the same records, and the
7-day window is a **subset** of the 28-day window. So the ratio is bounded above
by 1.0 by construction:

```
acwr(600.0, 600.0) == 1.0     # every session inside the acute window
acwr(600.0, 1500.0) == 0.4    # spread evenly across four weeks
```

`1.0 >= 1.5` is never true. A sweep of 3600 database shapes -- every
combination of 0-9 acute days, 0-9 chronic days, three session durations, three
average heart rates, present and absent `hr_max`, resolved and open reviews --
never produced `deload` once.

Conventional acute:chronic work compares like with like: an acute *weekly*
average against a chronic *weekly* average, which is why ratios above 1.5 are
ordinary there. Here the chronic figure is a raw 28-day sum, so the comparison
is between a week and a month.

**Consequence.** When the athlete is ramping hardest -- all load concentrated in
the last week, ratio pinned at its 1.0 ceiling -- the system reads that as the
*build* band and says nothing about backing off. The one state that should fire
under heavy acute load is the one state that cannot fire at all.

**Not fixed here.** Choosing a scaling is a coaching decision: divide chronic by
four, or use 14-day against 28-day, or rescale the bands to match the current
formula. Any of those changes what the athlete is told, so the bands should be
set deliberately rather than by whoever writes the next patch. Until then the
ceiling is asserted in the test suite so it cannot move unnoticed.

## 2. The 1.3-1.5 caution band is dead

Same cause. `CAUTION_ACWR = 1.3` is above the 1.0 ceiling. The band between
`LOW_ACWR` and `CAUTION_ACWR` is the only populated one, and the state above it
does not exist.

## 3. `recover` is advertised but unreachable

`terms.STATE_RECOVER` is in `CONTROL_STATES`, so `recommend.available_states()`
returns it and anything rendering the state list offers an option the policy
cannot produce. `recommend()` has no branch that returns it.

Unlike the two above, this one is structural rather than arithmetic: there is
simply no code path. Either the state needs a policy or it should stop being
advertised. It is currently advertised, which means a reader of the state list
may wait for a recommendation that cannot arrive.

## 4. A missing input is reported as missing history

When `hr_max` is absent, every run fails `run_session_load`, and `compute()`
**skips those runs entirely** rather than counting them:

```python
load, conf, note = run_session_load(row, hr_max)
if load is None:
    run_notes.append({...})
    continue          # never reaches run_days
```

So ten logged runs with no `hr_max` present as `runs_28d = 0`, and the
rationale reads:

```
only 0 runs in 28 days, need 8
```

The athlete is told they lack history when the real problem is one absent
number. Same for runs recorded without `avg_hr`.

Two further branches are dead as a direct consequence:

- `if w28["run_load"] is None` -- unreachable, because `runs_28d >= 8` already
  implies every counted run had a computable load
- `if ratio is None` -- unreachable, because chronic sums above zero whenever
  `runs_28d >= 8`

**Consequence.** The `unavailable` state the brief asks for is never entered.
A missing input is currently indistinguishable from an empty history, which is
the opposite of what the null-versus-zero discipline elsewhere in the system is
for.

## What is reachable

Confirmed by sweep: `build`, `maintain`, `data_insufficient`,
`confirmation_required`.

Also worth recording, because it is easy to get wrong: **`runs_7d` and
`runs_28d` count distinct days, not sessions.** Two runs on the same day
collapse into one. `MIN_RUNS_7D = 3` means three days with runs, not three
runs.

## Live state

The athlete's own data currently returns `confirmation_required` with 11
unconfirmed activities. That is the policy working correctly: the refusal
outranks the load figures, which is the intended behaviour. It is also, right
now, the only thing standing between the athlete and a recommendation, because
of defect 1.

## Standing note

`terms.py` describes this as "a training-control signal", not a risk score, and
the disclaimers are correct. Defects 1 and 2 do not make the system dangerous:
it never advises more than the evidence supports, and it refuses readily. They
make it incomplete in the one direction that matters when someone is doing too
much, and they make it honest-sounding for the wrong reason when an input is
missing.
