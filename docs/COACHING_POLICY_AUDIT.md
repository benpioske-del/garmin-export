# Coaching policy audit

Generated by writing the rationale fixtures, not by reading the code.
`tests/test_recommend_snapshots.py` holds the evidence and re-checks every
claim on this page on each run.

**Status: all four defects fixed.** Sections 1 to 4 are kept in their original
wording as the record of what was wrong, because "this used to be broken and now
is not" is the useful part. Each is marked with what changed. The tests that pin
them are now inverted: they assert the fix, so reintroducing any of these fails
the suite rather than passing quietly.

Four defects. Three of them meant the policy was quieter than it looked.

## 1. `deload` cannot be produced

> **Fixed.** `loadcalc.acwr` now compares the acute week against the *mean*
> chronic week, so the ratio can exceed 1.0 and every bound above it is live.
> See "The ratio, stated once" below.

This is the important one.

```
loadcalc.acwr(acute, chronic) -> round(acute / chronic, 2)
recommend: HIGH_ACWR = 1.5
```

`acute` is the 7-day combined load and `chronic` is the 28-day combined load.
Both are sums of non-negative per-session loads over the same records, and the
7-day window is a **subset** of the 28-day window. So the ratio is bounded above
by 1.0 by construction:

```
acwr(600.0, 600.0) == 1.0     # every session inside the acute window
acwr(600.0, 1500.0) == 0.4    # spread evenly across four weeks
```

`1.0 >= 1.5` is never true. A sweep of 3600 database shapes -- every
combination of 0-9 acute days, 0-9 chronic days, three session durations, three
average heart rates, present and absent `hr_max`, resolved and open reviews --
never produced `deload` once.

Conventional acute:chronic work compares like with like: an acute *weekly*
average against a chronic *weekly* average, which is why ratios above 1.5 are
ordinary there. Here the chronic figure is a raw 28-day sum, so the comparison
is between a week and a month.

**Consequence.** When the athlete is ramping hardest -- all load concentrated in
the last week, ratio pinned at its 1.0 ceiling -- the system reads that as the
*build* band and says nothing about backing off. The one state that should fire
under heavy acute load is the one state that cannot fire at all.

**Not fixed here.** Choosing a scaling is a coaching decision: divide chronic by
four, or use 14-day against 28-day, or rescale the bands to match the current
formula. Any of those changes what the athlete is told, so the bands should be
set deliberately rather than by whoever writes the next patch. Until then the
ceiling is asserted in the test suite so it cannot move unnoticed.

## 2. The 1.3-1.5 caution band is dead

> **Fixed** by the same change as defect 1. The band is reachable and has a
> scenario of its own (caution-band-spike, ratio 1.33).

Same cause. `CAUTION_ACWR = 1.3` is above the 1.0 ceiling. The band between
`LOW_ACWR` and `CAUTION_ACWR` is the only populated one, and the state above it
does not exist.

## 3. `recover` is advertised but unreachable

`terms.STATE_RECOVER` is in `CONTROL_STATES`, so `recommend.available_states()`
returns it and anything rendering the state list offers an option the policy
cannot produce. `recommend()` has no branch that returns it.

> **Fixed.** `recommend()` now returns `recover` when the gap since the last run
> is `RECOVER_GAP_DAYS` or more. The branch sits ahead of the thin-window
> refusal that used to mask it: an athlete three weeks into a break has an empty
> acute window, and describing that arithmetic was never the useful answer.
> Scenario: `recover-after-gap`.

Unlike the two above, this one is structural rather than arithmetic: there is
simply no code path. Either the state needs a policy or it should stop being
advertised. It is currently advertised, which means a reader of the state list
may wait for a recommendation that cannot arrive.

## 4. A missing input is reported as missing history

> **Fixed** by ordering. The load-availability branch now runs before the
> MIN_RUN_DAYS_28D count check, so the refusal names the absent input
> instead of the run count it caused.

When `hr_max` is absent, every run fails `run_session_load`, and `compute()`
**skips those runs entirely** rather than counting them:

```python
load, conf, note = run_session_load(row, hr_max)
if load is None:
    run_notes.append({...})
    continue          # never reaches run_days
```

So ten logged runs with no `hr_max` present as `runs_28d = 0`, and the
rationale reads:

```
only 0 runs in 28 days, need 8
```

The athlete is told they lack history when the real problem is one absent
number. Same for runs recorded without `avg_hr`.

Two further branches are dead as a direct consequence:

- `if w28["run_load"] is None` -- unreachable, because `runs_28d >= 8` already
  implies every counted run had a computable load
- `if ratio is None` -- unreachable, because chronic sums above zero whenever
  `runs_28d >= 8`

**Consequence.** The `unavailable` state the brief asks for is never entered.
A missing input is currently indistinguishable from an empty history, which is
the opposite of what the null-versus-zero discipline elsewhere in the system is
for.

## What is reachable

All six advertised states are reachable, and a sweep of the database shape space
asserts it rather than trusting the scenario list:

`build`, `maintain`, `recover`, `deload`, `data_insufficient`,
`confirmation_required`.

`deload` and `recover` were unreachable until the fixes above. The sweep test is
the thing that would catch a regression, because it fails loudly rather than
letting a band quietly die again.

Also worth recording, because it is easy to get wrong: **the gates count distinct
days, not sessions.** Two runs on the same day collapse into one. The constants
are named `MIN_RUN_DAYS_7D = 3` and `MIN_RUN_DAYS_28D = 8`, so three days with
runs, not three runs. The evidence keys are `run_days_7d` and `run_days_28d` and
the refusal strings say "training days".

## The ratio, stated once

    ratio = 7-day total / (28-day total / 4)

Acute is a week. Chronic is a mean week. This is the canonical acute:chronic
workload ratio, and it is why the bounds `0.8`, `1.3` and `1.5` mean what the
comments say they mean. Comparing the two window sums instead — the old form —
cannot produce a value above 1.0, because the 7-day window is a subset of the
28-day one. Every bound above 1.0 was therefore dead.

At the fixed instant used by the fixtures:

| shape | ratio | state |
|---|---|---|
| 3 acute days, 8 chronic | 1.09 | `build` |
| 4 acute days, 8 chronic | 1.33 | `maintain` (caution band) |
| 5 acute days, 8 chronic | 1.54 | `deload` |
| 3 acute days, 18 chronic | 0.57 | `maintain` (low, no volume added) |
| 0 acute days, gap of 8 | n/a | `recover` |

## Live state

The athlete's own data currently returns `confirmation_required` with 11
unconfirmed activities. That is the policy working correctly: the refusal
outranks the load figures, which is the intended behaviour.

It is now the *only* thing standing between the athlete and a recommendation.
The four defects above are fixed, so once those 11 records are confirmed the
system will produce a real control state rather than reporting missing history
for a reason that was never true. The live ratio, computed on the 28-day window
regardless, is 0.93 — inside the build band.

## Standing note

`terms.py` describes this as "a training-control signal", not a risk score, and
the disclaimers are correct.

The distinction worth keeping: defects 1 and 2 did not make the system dangerous.
It never advised more than the evidence supported, and it refused readily. They
made it incomplete in the one direction that matters when someone is doing too
much, and made it honest-sounding for the wrong reason when an input was missing.

The `recover` branch is the one piece of genuinely new policy here. It triggers
on a training gap of `RECOVER_GAP_DAYS = 7` or more and advises a one-to-two-week
gradual return. The bound is deliberately conservative and the state carries no
volume target, so it can only ever reduce what the system proposes.
